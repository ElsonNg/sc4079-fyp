Candidate regions are embedded independently. The current implementation does not average all region embeddings. It groups retrieval hits by corpus region-pair identity, ranks aggregates by their best similarity, and retains support information such as the number of candidate regions and granularities involved.

      } else if (typeof proxyValue.auth === 'object') {
        throw new AxiosError('Invalid proxy authorization', AxiosError.ERR_BAD_OPTION, { proxy: proxyValue });
      }

      const encodedCredentials = Buffer.from(proxyValue.auth, 'utf8').toString('base64');

      requestOptions.headers['Proxy-Authorization'] = 'Basic ' + encodedCredentials;
    }

    requestOptions.headers.host = requestOptions.hostname + (requestOptions.port ? ':' + requestOptions.port : '');
    const targetProxyHost = proxyValue.hostname || proxyValue.host;
    requestOptions.hostname = targetProxyHost;
    // Replace 'host' since options is not a URL object
    requestOptions.host = targetProxyHost;
    requestOptions.port = proxyValue.port;
    requestOptions.path = requestTarget;
    if (proxyValue.protocol) {
      requestOptions.protocol = proxyValue.protocol.includes(':') ? proxyValue.protocol : `${proxyValue.protocol}:`;
    }
  }

  requestOptions.beforeRedirects.proxy = function beforeRedirect(nextRedirect) {
    // Configure proxy for redirected request, passing the original config proxy to apply
    // the exact same logic as if the redirected request was performed by axios directly.
    setProxy(nextRedirect, proxySettings, nextRedirect.href);
  };

For this C01 comparison: the candidate and vulnerable regions have the same AST shape, token roles, and overall construction, so those three scores are 1.0. The patched region adds an if (!shouldBypassProxy(location)) guard, changing its AST shape, call set, and token sequence. That is why its structural, token, and semantic scores are lower.

How the two sides become a decision

The verifier calculates the same weighted side score twice: once against the vulnerable region and once against its paired patched region. It then computes the vulnerable-minus-patched margin:

vulnerable_score = compare(candidate, vulnerable_region)
patched_score    = compare(candidate, patched_region)
margin           = vulnerable_score - patched_score

A candidate is provisionally flagged when the vulnerable score is at least 0.75 and the margin is at least 0.08. It is cleared when the same margin is at most -0.08; values between those boundaries become manual_review. There is one configured margin threshold, interpreted symmetrically. The current implementation then uses support count, granularity diversity, and a larger margin to assign provenance confidence.

Where the score weights came from

The active verifier now uses equal weights. This deliberately avoids pretending that the previous hand-set hierarchy was empirically calibrated:

ComponentWeightDesign rationale
AST structural similarity33.3% One of three equally weighted signals; it remains the primary conceptual signal because syntax structure should survive identifier renaming and formatting changes.
Role/token similarity33.3% Preserves operation order, keywords, and operators while abstracting ordinary identifier names.
Semantic feature overlap33.3% Uses calls, member accesses, and literals as a third independent local clue.
Local source/alignment similarityExcluded Disabled from the active score; its helper remains available for a later ablation.

The active component weights sum to 1.0. There are also provisional internal weights:

  • AST structure: 55% AST-shape sequence similarity, 25% AST-path sequence similarity, 20% exact node-type match.
  • Role/token similarity: 75% normalized role-token sequence similarity, 25% operator-set overlap.
  • Semantic features: 50% call overlap, 30% member-access overlap, 20% literal overlap.
Objective status: equal weighting is a deliberately simple starting assumption, not evidence-derived calibration. The current positive-only fixture cannot tell us whether equal weighting is optimal because it contains no benign or patched negatives and therefore cannot measure precision or false positives. A defensible next step is to freeze a held-out, advisory-disjoint validation set and compare or fit weights against flagged, cleared, and manual-review outcomes.

What the thresholds and confidence checks mean

CheckCurrent valueMeaningHow it was chosen
Minimum vulnerable score 0.75 Requires the candidate to have a reasonably strong direct comparison with the vulnerable region before it can be flagged. Provisional engineering threshold. It has not been calibrated against a held-out set.
Minimum margin +0.08 Requires the vulnerable comparison to beat the patched comparison by at least 0.08. High similarity to both sides is therefore not enough to flag. Provisional separation margin intended to prevent near-ties from becoming automatic findings.
Negative side of margin ≤ −0.08 If vulnerable_score − patched_score ≤ −0.08, the patched side clearly wins and the candidate is classified as cleared. This uses the same minimum_margin value as the positive side; there is no separate clear-gate parameter. Symmetric interpretation of the one margin threshold.
Support for confidence support_count ≥ 3 At least three distinct candidate regions retrieved the same corpus region-pair. This is evidence that the match is not supported by only one outlier region. Heuristic confidence signal; it does not change the flagged/manual/cleared status.
Granularity support granularity_count ≥ 2 The same corpus pair is supported by at least two candidate region types, such as changed, block, context, or function. Heuristic diversity signal intended to reward agreement across resolutions.
High-confidence margin margin ≥ +0.15 Requires a stronger vulnerable-over-patched separation before the result can receive high provenance confidence. Provisional stricter margin; not calibrated to a measured precision target.
Threshold status: these values were configured as initial, conservative-looking engineering defaults while the region pipeline was being built. They were not learned from the 30-case positive fixture, because that fixture contains no benign or patched negative cases. Proper calibration requires advisory-disjoint vulnerable positives plus patched and benign negatives, followed by measuring precision, recall, abstention, and false-positive rates across candidate thresholds.

8. What this example does and does not prove

  • It demonstrates the mechanics of the current detector on one known positive candidate.
  • It does not prove that the candidate is vulnerable from semantics alone; C01 is a generated positive fixture derived from a known vulnerable corpus entry.
  • The thresholds are provisional and were not calibrated on a held-out negative set.
  • The final 30-case evaluation contained positives only, so this walkthrough says nothing about false-positive rates.
  • The HTML reflects the current implementation, including its max-similarity-first aggregation and disabled local-alignment helper.
